## 3-3 — 동일 입력 결과 편차 최소화(결정성)

**결과 문장(문서에 남길 것):**
> 동일 입력(나이 고정)으로 추론을 100회 반복한 결과 예측확률·점수·등급의 편차는 **0.0(비트 단위 일치)**였다. 배포 아티팩트는 SHA-256으로 고정·검증하며, 시계를 고정한 전체 파이프라인(프로필→나이계산→코호트표 조회→점수) 반복에서도 결과가 동일했다. (생일 경과에 따른 나이·점수 변화는 의도된 동작이다.)

**검증 방식(`app/tests/ml/test_determinism.py`, 6 tests 통과):**

- ① 추론 결정성: `predict_sync` 100회 → `risk_score`·`muscle_score`·`score_band` 전부 `==`(근사비교 아님). 두 아티팩트 모두.
- ② 아티팩트 무결성: SHA-256 고정값 검증(`ARTIFACT_HASHES.txt`).
- ③ 시스템 결정성: 시계 고정 후 전체 경로 50회 동일.

로지스틱 회귀의 `predict_proba`는 순수 행렬연산이라 같은 입력·같은 모델이면 비트 단위로 결정적이다. 따라서 `==` 비교가 정당하다.

## 3-2 — 비동기 처리 (참고)

`app/ml/predictor.py`의 `async predict()`가 추론을 `run_in_executor`로 이벤트 루프에서 분리해, 추론 중 API 응답성이 유지된다. 3-2의 근거로 재사용 가능.

## 실행 방법

```bash
# 성능 재현 (KNHANES 처리본 필요)
uv run --group app --with pyarrow python scripts/ml/evaluate_model.py \
  --data_dir <데이터폴더> --out_dir scripts/ml

# 결정성 테스트
pytest app/tests/ml/test_determinism.py -v

# ML 테스트 전체(기존 15 + 결정성 7 = 22)
pytest app/tests/ml/ -v
```
데이터가 없어도 `scripts/ml/metrics.json`·`metrics.csv`에 산출값이 커밋돼 있어 수치 확인 가능.

> 결정성 테스트는 기존 `app/tests/ml/test_predictor.py`(아티팩트 계약 테스트 10건)를 **덮어쓰지 않고 별도 파일**로 둔다.
> 계약 테스트는 검증 요약 문서가 근거로 인용하는 대상이라 함께 유지되어야 한다.

## 예상 질문 대비

심사·발표에서 표를 보면 나올 법한 질문과 답. 근거는 모두 문서에 이미 있고, 아래는 **말로 답할 형태**로 정리한 것이다.

**Q1. days와 binary가 성능이 같은데 왜 인코딩을 바꿨나?**
성능을 올리려고 바꾼 것이 아니다(AUROC 0.8227 vs 0.8220, 사실상 동일). 일수 인코딩이라야 "근력 운동을 하루 늘리면 점수가 얼마나 오르는가"라는 what-if를 계산할 수 있고, 이게 챌린지 UX의 핵심이다. **성능 손실 없이 제품 기능을 얻은 사례**로 보는 게 정확하다. (이력 문서 4항)

**Q2. ECE가 전체(0.0053)보다 각 fold(0.012~0.023)에서 더 나쁜데?**
정상이다. 전체 OOF는 보정 구간(bin)당 표본이 약 5배라 추정이 안정적이고, fold별로 서로 반대 방향의 편차가 상쇄된다. **다른(더 좋은) 모델이 아니라 같은 예측값을 더 큰 표본에서 잰 것**이다.

**Q3. minimal과 with_waist를 같은 표본에서 비교한 건가?**
아니다. 4,279 vs 4,266으로 허리둘레 결측 13행 차이가 있다. 0.3%라 관측된 성능 차이를 설명하기엔 너무 작지만, 엄밀히 짝지어진 비교는 아니라는 점은 문서에 명시해 두었다.

**Q4. 내부 검증만 한 것 아닌가?**
맞다. 단일 데이터셋 OOF이며 외부 코호트 검증은 미수행이다. 숨기지 않고 「한계」 절에 명시했다. 표본이 "악력+BIA 동시 측정자"로 한정된 선택편향도 IPW로 점검했고(효과 +0.29%p), 미미해 최종 모델엔 적용하지 않았다.

**Q5. 왜 로지스틱 회귀인가? 요즘은 부스팅을 쓰지 않나?**
실제로 비교했고 로지스틱이 더 좋았다(AUROC 0.8227 vs 0.786, AUPRC 0.4361 vs 0.377). 특히 **보정에서 격차가 크다**(ECE 0.0053 vs 0.0513). 이 서비스는 확률을 그대로 점수로 노출하므로 보정이 순위 품질보다 중요하다. (이력 문서 6항)

**Q6. 클래스 불균형인데 class_weight를 왜 안 썼나?**
써 봤고, 판별력은 거의 그대로인데 **보정이 붕괴했다**(ECE 0.0053 → 0.238, 평균 예측확률 13% → 37%). 확률을 화면에 그대로 쓰는 구조에서는 치명적이라 비가중을 택했다. 불균형은 가중이 아니라 **AUPRC를 기준선 대비로 읽는 방식**으로 다뤘다. (이력 문서 10항)
