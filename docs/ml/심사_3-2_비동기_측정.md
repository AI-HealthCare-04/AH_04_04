# 심사 3-2 — 추론 비동기 처리 측정 결과

## 결론 요약

`app/ml/predictor.py` 의 `RiskPredictor.predict()` 는 블로킹 추론을 `loop.run_in_executor()` 로 위임한다. **적용은 되어 있다.** 그 효과를 측정한 결과, **현재 모델에서는 유의미한 개선이 관측되지 않았다.**

원인까지 규명했다. 이 추론은 **GIL 을 놓지 않는 작업**이라, 스레드로 넘겨도 이벤트 루프가 풀리지 않는다.

수치를 부풀리지 않고 관측된 대로 기록한다. 이 문서 자체가 "측정했고, 효과가 없음을 확인했고, 이유를 안다"는 근거다.

## 무엇을 왜 이렇게 측정했는가

**단일 호출 지연을 재면 안 된다.** 스레드풀 디스패치 오버헤드 때문에 비동기 쪽이 오히려 느리게 나오고, 그 숫자는 이 설계의 목적과 무관하다. 비동기 경계의 목적은 한 요청을 빠르게 만드는 것이 아니라, **한 요청이 이벤트 루프를 점유해 다른 모든 요청을 막는 것을 방지**하는 것이다.

그래서 예측 엔드포인트에 동시 부하를 거는 **동안**, 아무 일도 하지 않는 가벼운 엔드포인트(`/health`)의 응답 지연을 관측했다. 이벤트 루프 점유가 실제로 해치는 값이 이것이다.

| 조건 | 내용 |
| --- | --- |
| A. 기준선 | 부하 없음. `/health` 만 호출 |
| B. 블로킹 | 추론을 async 라우트에서 직접 호출(이벤트 루프 점유) |
| C. executor | 추론을 `run_in_executor` 로 위임 (**현재 배포 구현**) |

## 후속 재측정 결과 (#368, 공식 실행)

부하 생성기를 별도 프로세스로 격리한 개선 스크립트로 동시성 16, 조건당 60초, 20코어 Windows / Python 3.13 / `workers=1`에서 실행했다. 원본은 `scripts/bench/results/async_bench_pr369-review-20260801.json`에 보존한다.

| 조건 | n | health P50 | P95 | P99 | 예측 RPS |
| --- | ---: | ---: | ---: | ---: | ---: |
| A. 부하 없음(기준선) | 1,986 | 3.27ms | 5.62ms | 7.35ms | — |
| B. 블로킹 추론 | 1,968 | 3.67ms | 8.65ms | 11.34ms | 182.7 |
| C. run_in_executor | 1,957 | 3.91ms | 8.93ms | 12.68ms | 176.3 |

각 부하 조건에서 1,900개가 넘는 표본을 확보해 P99를 최댓값이 아닌 백분위로 해석할 수 있다. B와 C의 P95는 8.65ms와 8.93ms, P99는 11.34ms와 12.68ms로 **executor의 응답성 개선이 관측되지 않았다.** 처리량도 같은 규모다.

기존 회차에서 보인 550ms 내외의 절대 지연은 부하 생성과 probe가 같은 클라이언트 이벤트 루프를 공유한 측정 오염이 대부분이었다. 프로세스 격리 후에는 사라졌지만 **B와 C가 사실상 같다는 상대 비교 결론은 그대로 재현됐다.**

즉 현재 모델에서는 **`run_in_executor`의 이벤트 루프 보호 효과가 관측되지 않는다.**

### 기존 측정 (#363, 참고)

동시성 16, 조건당 20초, 20코어 / Python 3.13. 같은 조건으로 2회 반복한 값이다.

| 조건 | health P50 | P95 | P99 | 예측 RPS |
| --- | ---: | ---: | ---: | ---: |
| A. 부하 없음(기준선) | 3.61ms | 5.54ms | 6.97ms | — |
| B. 블로킹 추론 | 176.41ms | 595.99ms | 938.49ms | 148.5 |
| C. run_in_executor | 192.79ms | 545.27ms | 652.36ms | 153.5 |

1회차(참고): B P95 583.72ms / P99 1177.94ms, C P95 489.71ms / P99 1468.93ms. 이 회차는 당시 stdout 수동 기록만 남고 원본 JSON은 보존되지 않았다. 후속 이슈 #368부터는 회차별 JSON을 별도 보존한다.

**정정된 해석**: 이 절대값에는 공유 클라이언트 이벤트 루프의 스케줄링 지연이 섞였으므로 서버 지연 근거로 사용하지 않는다. B/C 상대 비교는 후속 격리 측정에서도 재현됐다. 표의 P99도 부하 조건별 표본이 약 77개뿐이라 최댓값으로 퇴화해 결론 근거로 사용하지 않는다.

## 왜 효과가 없는가

### ① 추론은 실제로 이벤트 루프를 오래 잡는다

| 구간 | 소요 |
| --- | ---: |
| `load_model_bundle` | 0.000ms (`lru_cache` 로 캐시됨) |
| `normalize_features` | 0.002ms |
| DataFrame 생성 | 0.119ms |
| **`predict_proba`** | **2.101ms** |
| **`predict_sync` 합계** | **2.379ms** |

2.4ms 는 무시할 수 없는 점유 시간이다. 그리고 그 **88% 가 `predict_proba`** 다. 단일 행 로지스틱 회귀의 수학 자체는 미미하고, 대부분 sklearn Pipeline 의 입력 검증·변환 오버헤드다.

> 참고: 모델 로드가 0ms 인 것은 `load_model_bundle` 에 `@lru_cache` 가 걸려 있어서다. 이 부분은 이미 잘 되어 있다.

### ② 그런데 그 작업이 GIL 을 놓지 않는다

같은 작업을 4개 스레드로 나눠 실행해 봤다.

```
직렬 400회    :  937.2ms
4스레드 400회 : 1015.9ms
속도향상      : 0.92x
```

**1.0 을 넘지 못한다.** 스레드를 늘려도 전혀 빨라지지 않는다는 것은 이 작업이 실행 내내 GIL 을 쥐고 있다는 뜻이다.

`run_in_executor` 는 작업을 **다른 스레드로 옮길 뿐 GIL 을 놓게 만들지 않는다.** 옮겨간 스레드가 약 2.4ms 동안 GIL 을 계속 쥐고 있으면, 그동안 이벤트 루프도 실행되지 못한다. 결국 B 와 C 가 같아진다.

이것은 구현 실수가 아니라 **Python 런타임의 구조적 제약**이다. `run_in_executor` 가 이벤트 루프를 지켜주는 것은 오프로딩된 작업이 GIL 을 놓을 때(파일·네트워크 I/O, 또는 GIL 을 해제하는 대형 BLAS 연산)뿐이다.

## 그렇다면 `run_in_executor` 를 유지해야 하는가

**유지하는 쪽을 권한다.** 근거는 세 가지다.

1. **측정상 큰 비용은 없다.** 후속 실행은 182.7 vs 176.3 RPS(-3.5%)였고 기존 실행은 148.5 vs 153.5로 방향이 뒤집혔다. 현재 측정만으로 지속적인 처리량 손실을 주장할 수 없다.
2. **모델이 바뀌면 즉시 값을 한다.** 앙상블·트리 계열·배치 추론처럼 내부에서 GIL 을 해제하는 연산 비중이 커지면 이 경계가 그대로 효과를 낸다. 그때 API 계층을 고칠 필요가 없다.
3. **경계가 문서화되어 있다.** 지금은 효과가 없다는 사실과 그 조건(GIL 해제 여부)을 알고 있으므로, 모델 교체 시 무엇을 다시 재야 하는지가 명확하다.

다만 **"비동기 처리로 추론 성능을 개선했다"고 주장하지는 않는다.** 측정 결과가 그것을 뒷받침하지 않는다.

## 실제로 응답성을 개선하려면

이 측정이 알려주는 개선 방향은 비동기가 아니라 다른 쪽이다. 필요해지면 검토할 순서로 적는다.

1. **`predict_proba` 오버헤드 축소** — 2.101ms 의 대부분이 단일 행에 대한 Pipeline 검증·변환이다. 최대 효과 지점이며 아키텍처를 건드리지 않는다.
2. **워커 프로세스 수 증가** — GIL 은 프로세스 단위이므로 uvicorn 워커를 늘리면 선형에 가깝게 확장된다. 현재 측정은 `workers=1` 기준이다.
3. **`ProcessPoolExecutor`** — GIL 을 우회하지만 2.5ms 작업에 IPC 오버헤드를 붙이는 것이라 현재 규모에서는 권하지 않는다.

## 재현 방법

```bash
uv run --no-sync python scripts/bench/async_bench.py --concurrency 16 --seconds 60
```

부하 측정·추론 분해·GIL 판별이 한 번에 실행된다. 60초는 부하 조건에서도 health 표본 100개 이상을 확보해 P99를 보고하기 위한 기본 측정 시간이다. 최신 결과는 `scripts/bench/async_bench_result.json`, 각 실행 원본은 `scripts/bench/results/async_bench_<run-id>.json` 에 저장된다. 같은 run ID가 이미 있으면 서버를 띄우기 전에 즉시 실패하고, 최종 쓰기도 exclusive create로 보호하므로 회차가 조용히 유실되지 않는다. 심사 근거로 사용하는 공식 실행의 회차 파일은 저장소에 함께 커밋한다.

후속 측정(#368)은 다음을 함께 기록·보호한다.

- 부하 생성기를 별도 프로세스로 분리해 health probe의 클라이언트 이벤트 루프와 격리
- 선형 보간 percentile 사용, 표본 100개 미만이면 P99 미보고
- OS/platform·CPU·Python·서버 worker 수·측정 시각을 JSON meta에 기록

**프로덕션 코드는 수정하지 않았다.** 비교용 블로킹 라우트는 벤치 스크립트가 자체적으로 소유하며, 실제 서비스 라우터에는 존재하지 않는다.

## 측정의 한계

- DB·인증을 거치지 않고 **추론 경계만 격리**해 측정했다. 실제 라우트에는 async DB I/O 가 함께 있으나 그쪽은 이미 논블로킹이라 이 비교의 결론을 바꾸지 않는다. 오히려 DB 지연이 섞이면 재려는 신호가 묻힌다.
- 전체 스택의 P95(심사 5-1)는 별도 측정 대상이다. 이 문서의 수치를 5-1 근거로 쓸 수 없다.
- 단일 머신(20코어, Windows) 1종에서만 측정했다. 절대값은 환경에 따라 달라지며, 의미가 있는 것은 **A/B/C 간 상대 비교**다.
- `workers=1` 기준이며 현재 운영 배포 구성과 같다. worker 수를 바꾸면 처리량 절대값이 달라지므로 JSON meta에 고정 기록한다.
- 이 문서의 기존 P99는 B/C 각각 약 77개 표본이라 최댓값과 같아 꼬리 백분위로 해석하지 않는다. 개선된 스크립트는 n<100이면 P99를 `null`로 남긴다.
- 기존 회차는 부하 생성과 health probe가 같은 클라이언트 이벤트 루프를 공유해 절대 지연에 클라이언트 측 스케줄링이 일부 섞였을 수 있다. B/C 상대 비교 결론은 재실행에서도 유지됐지만, #368 이후 측정은 두 경로를 별도 프로세스로 분리한다.
