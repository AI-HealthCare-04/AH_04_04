## 1. 무엇을 왜 받는가

### `health_profiles` — 근육 건강 점수 예측의 입력

| 항목 | 목적 | 없으면 |
|---|---|---|
| `birth_date` | **만 나이** 산출 → 코호트 조회 키·예측 제공 여부 판정 | 점수·또래 비교 불가 |
| `sex` | 코호트 조회 키(성별 분리 표) | 또래 비교 불가 |
| `height_cm` · `weight_kg` · `bmi` | 모델 입력 | 예측 불가 |
| `waist_cm` (선택) | 허리 포함 모델·코호트 선택 | 허리 제외 모델로 계산 |
| `walk_days` · `musc_days` | 모델 입력(활동량) | 예측 불가 |
| `kidney_status` · `protein_restriction_status` | **고단백 식사 미션 노출 게이트**(#304) — 예측 입력 아님 | 안전을 위해 미션 차단 |

**생년월일을 연도로 줄이지 않는 이유** — #408 논의에서 제가 제안했다가 철회한 항목입니다.

- 코호트 조회 키가 연령대가 아니라 **단일 나이**입니다: `_cohort_age_key(float(age))` (`app/ml/predictor.py`)
- 예측 제공 여부도 만 나이 기준입니다: `AGE_MIN = 65` 미만이면 `AgeNotSupportedError`
- 출생연도만 남기면 생일 전후로 1년이 어긋나고, **64→65 경계에서는 제공 여부 자체가 달라집니다**

즉 컬럼 하나를 줄이는 대신 정확도와 API 계약을 흔드는 거래라 이득이 없습니다.

### 활동 로그

미션·걷기·식사·게임·5STS 기록. 코치님 피드백에서도 "서버에 남겨도 된다"고 한 범주입니다.

## 2. 서버에 남는 것 / 남지 않는 것

### 남지 않음 — 예측 입력 원본 (2026-08-03 폐기, [#410](https://github.com/AI-HealthCare-04/AH_04_04/pull/410))

예측 1건마다 정규화된 입력 전체(나이·성별·BMI·허리둘레)가 `risk_predictions.input_snapshot` 에 JSON 으로 **복제 저장**되고 있었습니다. 프로필 테이블을 아무리 줄여도 이 복제가 남으면 노출면은 그대로입니다.

런타임에 그 스냅샷을 읽는 곳은 또래 분포 하나뿐이고 필요한 값은 조회 키(나이 키·성별)뿐이라, **성별만 컬럼으로 승격**해 원본 없이 동작하게 하고 기존 행의 원본은 전량 삭제했습니다.

**배포 DB 실측** (EC2, 마이그레이션 `0021_drop_input_snapshot` 적용 후)

| 항목 | 값 |
|---|---|
| 예측 행 수 | 73 |
| **원본이 남아 있는 행** | **0** |
| 조회 키 백필 | 나이 키 결측 0 · 성별 73/73 |

### 남음 — `health_profiles`

1장의 항목이 그대로 저장됩니다. **재평가할 때마다 새 행이 만들어지며 생년월일·신장 상태·단백질 제한이 매번 복제됩니다.**

**배포 DB 실측**

| 항목 | 값 |
|---|---|
| 프로필 행 | 129 |
| 사용자 | 87 |
| 한 사용자의 최대 행 | **14** |

이 복제를 줄이는 것이 #408 **A+ 3번**이고, #396 의 하루 1회 판별(`input_method` 로 재평가 여부 구분)을 함께 옮겨야 해서 아직 남아 있습니다.

### 보관 기간

**별도 보관 기간을 두지 않습니다.** 계정이 살아 있는 동안 보관하고, 탈퇴 시 즉시 파기합니다(3장). 심사·시연용 프로젝트라 법령상 보존 의무가 걸리는 거래 기록이 없습니다.

## 3. 탈퇴 시 파기 — 즉시 물리 삭제

`POST /users/me/withdraw` ([#356](https://github.com/AI-HealthCare-04/AH_04_04/issues/356))

1. `users` 행을 `FOR UPDATE` 로 잠급니다 — 같은 사용자를 참조하는 동시 쓰기를 직렬화합니다
2. `purge_user_data` 가 **FK 그래프를 역추적**해 연결 데이터를 자식 → 부모 순서로 삭제합니다
3. `delete_account` 가 `users` 행을 삭제합니다
4. **전부 한 트랜잭션** — 도중 실패하면 롤백되어 어중간한 상태가 남지 않습니다

**익명화가 아니라 삭제입니다.** 행이 사라지므로

- 기존 토큰은 사용자 조회 실패로 즉시 401 이 됩니다
- `UNIQUE(provider, social_id)` 가 비워져 같은 소셜 계정 재로그인은 **복구가 아니라 신규 가입**입니다
- 원본 `social_id`·닉네임도 남지 않습니다
- 탈퇴 커밋 이후 도착하는 늦은 쓰기는 FK 위반으로 거부되어 파기 후 데이터가 되살아날 수 없습니다

파기 대상은 테이블 목록을 손으로 적지 않고 **메타데이터의 FK 그래프에서 산출**합니다. 새 테이블이 추가돼도 코드 수정 없이 파기·검증 대상에 포함되고, 테스트(`test_withdrawal.py`)가 같은 함수를 써서 파기와 검증의 대상 집합을 일치시킵니다.

## 4. 약관 본문과의 차이 — 개정이 필요합니다

`docs/terms/privacy-1.0.md` §3 이 **현재 구현과 다릅니다.**

> 현재는 계정 비활성화(soft-delete)까지 구현되어 있으며, 구체적 보존기간·물리 파기 절차는 파기정책 확정 후 확정 문서에 명시합니다(초안).

실제로는 3장대로 **즉시 물리 삭제**가 구현돼 있습니다. 문구가 실제보다 **약하게** 적혀 있어 사용자에게 불리한 방향은 아니지만, 사실과 다른 것은 맞습니다.

### 지금 고치지 않는 이유

약관 본문을 고치면 `docs/terms/README.md` 의 반영 절차상 **버전을 올려야 합니다**(`privacy-1.0` → `1.1`). 그러면 파일명·`terms_catalog.py`·재게시·배포 환경변수 3곳에 더해 **기존 1.0 동의자 재동의**가 필요합니다. 그 흐름이 [#372](https://github.com/AI-HealthCare-04/AH_04_04/issues/372) 이고 `[심사 종료 후]` 로 분류돼 있습니다. `sensitive-health` 1.0 → 1.1 개정 때 이미 같은 부채가 생겼습니다.

**심사 전에 재동의 부담을 하나 더 얹는 것보다, 실제 동작을 이 문서로 정확히 남기고 약관 개정은 #372 와 묶어 처리하는 편이 낫다고 판단했습니다.**

### 개정 시 반영할 문안 (초안)

> 회원탈퇴 시 저장된 개인정보와 연결 데이터를 **즉시 파기(물리 삭제)** 합니다. 계정 비활성화나 익명화 보관을 하지 않으며, 같은 소셜 계정으로 다시 가입하면 이전 데이터와 무관한 신규 계정이 됩니다.
