# v1 RC 통합 QA 실행 가이드

> **이 문서의 역할** — [#100](../../issues/100)이 "무엇을 확인할지(what)"의 목록이라면,
> 이 가이드는 **"어떻게 돌리고 증거를 어떻게 남길지(how)"** 의 실행 문서다.
> QA 결과는 워드/한글 파일이 아니라 아래 **§6 증거 템플릿**을 복사해 **#100 이슈 댓글**에 남긴다.

---

## 0. 언제 돌리나

릴리스 직전 한 번이 아니라 **각 릴리스 후보(RC) 빌드마다** 실행한다. 코드가 바뀌어 새 빌드를
올릴 때마다 이 절차를 다시 돈다(특히 배포가 걸린 `dev` 병합 이후).

---

## 1. 무엇이 "QA"이고 무엇이 아닌가 (혼동 방지)

우리 저장소의 "테스트" 관련 자산은 3층으로 나뉜다. QA(이 가이드)는 그중 **③ 수동 통합 검증**이다.

| 층 | 무엇 | 누가/언제 | 이 가이드와의 관계 |
|---|---|---|---|
| ① 자동 테스트 코드 | `app/tests/` (pytest), 안드로이드 unit test | **CI가 매 푸시 자동 실행** | 전제 조건. §2에서 "CI 초록" 한 줄로 확인만 한다 |
| ② seed 스크립트 | `scripts/seed_mission_templates.py` | QA/시연 **전에 1회 주입** | 사전 준비(데이터 세팅). QA 시나리오 자체는 아니다 |
| ③ 수동 통합 QA | 사람이 **실제 RC 빌드**를 조작하며 시나리오 확인·증거 기록 | RC 빌드마다 수동 | **← 이 가이드의 본체** |

### 2.1 기능 동결(freeze) — RC 포함 범위를 먼저 결정한다

동결한다. 동결 후 병합이 생기면 **새 RC**다(이 절차를 처음부터 다시).

### 2.2 기준점 기록 (증거에 그대로 들어간다)

동결 시점에 아래를 **전부** 기록한다. "앱 SHA 하나"로는 재현이 안 된다.

```bash
# Android 기준 SHA (android/dev 동결 커밋)
git rev-parse --short origin/android/dev
# 백엔드 기준 SHA (dev 동결 커밋) + 해당 커밋의 배포 워크플로 실행 링크(Actions run URL)
git rev-parse --short origin/dev
# 배포 서버가 실제로 그 SHA인지: 배포 워크플로 로그 또는 서버 헬스 엔드포인트로 확인
# DB 상태: 배포 DB 기준 migration head + seed 주입 여부
uv run alembic current        # (배포 환경 기준 — 실행 위치는 배포 담당(란)과 확인)
```

- **APK 식별**: 최종 게이트 APK의 `versionName/versionCode` + 파일 해시
  - macOS/Linux: `shasum -a 256 app-release.apk`
  - Windows(PowerShell): `Get-FileHash app-release.apk -Algorithm SHA256`

### 2.3 빌드 2종 — 탐색은 debug, **최종 게이트는 배포 동일 APK**

| 용도 | 빌드 | 원칙 |
|---|---|---|
| 탐색 QA(시나리오 손에 익히기, 중간 회귀) | debug | 아무 시점이나 가능 |
| **최종 게이트(§6 판정)** | **release(서명) — 실제 배포할 동일 artifact** | 로컬 재빌드 금지. 아래 방법으로 확보한 APK의 해시를 기록하고, **그 파일로만** 최종 pass 판정 |

- **release APK 확보(권장)**: 동결 커밋의 CI/릴리스 워크플로 artifact를 내려받는다
  (Actions run → artifacts). 서명 포함 빌드가 없다면 서명 키 보유자(란)가 1회 빌드해
  해시와 함께 공유한다.
- 로컬 debug 빌드(탐색용):
  - macOS/Linux:
    ```bash
    cd android && ./gradlew --no-daemon :app:assembleDebug
    ```
  - Windows(PowerShell):
    ```powershell
    cd android; .\gradlew.bat --no-daemon --console=plain :app:assembleDebug
    ```
  - 산출물: `android/app/build/outputs/apk/debug/app-debug.apk`
- 설치(공통): `adb install -r <apk>` (무선 디버깅 또는 USB)

### 2.5 테스트 계정·시작 상태 매트릭스

⚠️ **매 시나리오 앱 데이터 삭제 금지.** 재실행 복원, 재로그인 기록 유지, 단백질 재진입·당일
재저장, 스트릭 중복 방지는 **상태 연속성이 있어야만 검증된다.** 초기화는 **"신규 상태가 필요한
그룹 시작 전"에만** 한다(각 그룹 헤더에 명시).

| Fixture | 상태 | 만드는 법 | 쓰는 그룹 |
|---|---|---|---|
| F-NEW | 신규 소셜 사용자(가입 전) | 앱 데이터 삭제 + 아직 가입 안 한 소셜 계정 | GP, AUTH |
| F-EXIST | 기존 소셜 사용자(온보딩 완료·기록 보유) | F-NEW로 GP-01 완주한 계정을 그대로 재사용 | AUTH, MEAL, STRK, REC |
| F-TERMS | 약관 동의 중단 상태 | 신규 가입 → 약관 화면에서 앱 종료 | AUTH-03 |
| F-GUEST | 게스트(체험) 세션 | 앱 데이터 삭제 → 체험으로 시작하기 | AUTH-04 |
| F-KIDNEY | 신장/단백질 제한 사용자 | 온보딩 건강체크에서 투석/신장질환 선택 | MEAL-01 |
| F-NORMAL | 제한 없는 일반 사용자 | 온보딩 건강체크 제한 없음 | MEAL-02~07 |
| F-STREAK | 스트릭 경계(어제까지 N일 연속) | 배포 DB에 seed/수동 조정 — 배포 담당(란)과 준비 | STRK-01~02 |

> 한 기기로 여러 fixture를 돌 때는 **F-EXIST 상태를 마지막까지 보존**하도록 순서를 짠다
> (권장 실행 순서: GP → AUTH(F-TERMS/F-GUEST는 별도 초기화) → ONB → MEAL → WALK/EXER/GAME/STS →
> DASH/PET/STRK → OFF/A11Y).

## 6. 증거 템플릿 (복사 → #100 이슈 댓글에 붙여넣기)

**Release gate 규칙**: `필수 항목(§4) 미실행 0 · FAIL(blocker) 0 · BLOCKED/N/A는 사유와
담당자(란) 승인 기록` — 셋 다 충족해야 RC 통과.

```md
### RC QA 실행 — YYYY-MM-DD HH:MM (테스터: ___)

#### 기준점 (§2.2)
- Android SHA:          (origin/android/dev 동결 커밋)
- 백엔드 SHA / 배포 run: (origin/dev 동결 커밋) / (Actions run URL)
- DB migration / seed:  (alembic head) / ✅❌
- APK: 종류(debug/release) · versionName/Code · SHA256 해시
  ⚠️ 최종 게이트는 release(배포 동일 artifact)만 인정
- CI(checks):           ✅ / ❌
- 기기:                 (모델 / Android 버전)  + 에뮬 320dp·글꼴 1.5배 여부

#### 결과 (항목 ID별 — PASS / FAIL / BLOCKED / N/A(사유))
| ID | 판정 | 증거(스크린샷·로그 링크) | 비고 |
|---|---|---|---|
| GP-01 | PASS | link | |
| AUTH-01 | ... | | |
| (…§3의 모든 ID를 나열한다. 미실행 항목도 BLOCKED/N/A로 반드시 기록…) |

#### FAIL 상세
- (ID) 증상 · 재현 절차 · blocker 여부 · 이슈 링크 #___
```
